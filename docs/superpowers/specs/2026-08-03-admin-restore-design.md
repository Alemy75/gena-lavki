# Восстановление бэкапа через админку — дизайн

Дата: 2026-08-03. Согласовано: **вариант A** — restore целиком внутри контейнера `app`,
загрузка бандла `.tgz` через интерфейс админки.

Дополняет [дизайн бэкапов](2026-07-29-backups-design.md): скачивание бэкапа из админки
уже есть (`GET /api/admin/backup`), теперь добавляем обратную операцию — восстановление
из того же формата бандла (`db.sql.gz` + `uploads.tgz` + `manifest.txt`).

## Цель

Восстановить сайт из бэкапа без SSH: админ выбирает файл `.tgz` на странице
«Резервная копия», подтверждает перезапись и получает результат. Покрывает оба
runbook'а из дизайна бэкапов, включая DR-сценарий «бэкап остался только на Mac».

## Рассмотренные подходы

| Подход | Вердикт |
|--------|---------|
| **A. Всё внутри контейнера `app`** (psql + prisma + tar уже в образе) | **Выбран**: без доступа к хосту, одинаково работает локально и в проде |
| B. Загрузка через админку, restore выполняет хост | Отпадает: нужен `docker.sock` в контейнере или агент на хосте — дыра в безопасности |
| C. Restore из серверной папки `backups/` без загрузки файла | Отпадает: не покрывает «бэкап только на Mac», требует менять compose |

## Решения (из брейнсторминга)

- **Старый бэкап** (схема БД отстаёт от кода): после заливки дампа роут сам запускает
  `prisma migrate deploy` — бэкап догоняется до текущей схемы, сайт сразу рабочий.
- **Страховка от «залил не тот файл»**: только предупреждение в UI с рекомендацией
  сначала скачать текущий бэкап (кнопка на той же странице). Без авто-снапшотов — YAGNI.
- **Подтверждение**: чекбокс «Я понимаю, что текущие данные будут перезаписаны»
  активирует красную кнопку.

## API — `POST /api/admin/restore`

Файл: `app/api/admin/restore/route.ts` (`runtime = "nodejs"`, `dynamic = "force-dynamic"`).

Поток:

1. **Auth**: `auth()` как в backup route — middleware на `/api/*` не распространяется.
   CSRF закрыт `SameSite=Lax` у сессионной cookie NextAuth (кросс-сайтовый POST
   cookie не получает).
2. **Приём файла**: тело запроса — сырой `.tgz` (без multipart), стримится во временный
   файл в `mkdtemp` — бандл не держим в памяти.
3. **Валидация**: `tar -xzf` во временный каталог; внутри обязаны быть `db.sql.gz`
   и `uploads.tgz`, иначе `400` и ничего не тронуто.
4. **БД**: `gunzip db.sql.gz` → `psql -v ON_ERROR_STOP=1 --single-transaction`
   к `db:5432`; параметры подключения — из `DATABASE_URL` (как `pgConn()` в backup
   route). Одна транзакция: битый дамп откатывается целиком, БД не повреждена.
   Дамп сделан с `--clean --if-exists`, поэтому объекты пересоздаются начисто.
5. **Миграции**: `prisma migrate deploy` (prisma установлена глобально в образе,
   каталог `prisma/` скопирован — та же команда, что в CMD контейнера).
6. **Uploads**: очистить `/app/public/uploads` и распаковать туда `uploads.tgz` —
   в самом конце, только после успеха БД (порядок как в `scripts/restore.sh`).
7. **Ответ**: JSON — успех или текст ошибки с указанием шага. Временные файлы
   удаляются в `finally`.

## UI — страница «Резервная копия»

Ниже кнопки скачивания — секция «Восстановление», клиентский компонент
`components/admin/restore-form.tsx` (страница остаётся серверной):

- выбор файла `.tgz`;
- предупреждение: перезаписывает ВСЕ данные; сначала скачайте текущий бэкап;
- чекбокс подтверждения → активируется красная кнопка «Восстановить»;
- на время операции — спиннер и блокировка формы (операция занимает десятки секунд);
- результат — текст успеха или ошибки из ответа API.

## Обработка ошибок

| Сбой | Состояние данных | Ответ |
|------|------------------|-------|
| Не архив / нет `db.sql.gz`/`uploads.tgz` | не тронуты | 400 с пояснением |
| Ошибка SQL при заливке | транзакция откатилась — не тронуты | 500, шаг «база данных» |
| `migrate deploy` упал | БД восстановлена, схема старая | 500, честно: БД залита, миграции нет; повторить или SSH + перезапуск контейнера |
| Ошибка распаковки uploads | БД новая, файлы старые | 500, честно: БД восстановлена, uploads нет; повторить restore |

Во время заливки дампа сайт может несколько секунд отдавать ошибки (таблицы
пересоздаются) — приемлемо для ручной редкой операции.

## Проверка

Локально через `docker compose up`:

1. Скачать бэкап через админку.
2. Удалить позицию каталога с картинкой.
3. Восстановить бандл через форму — позиция и картинка вернулись.
4. Залить заведомо битый файл (не tgz; tgz без `db.sql.gz`) — 400, данные не тронуты.
5. Скачать бэкап от кода до последней миграции (или вручную удалить строку из
   `_prisma_migrations` в дампе) — restore проходит, `migrate deploy` доводит схему.

## Ограничения (YAGNI)

- Без выбора «только БД» / «только файлы» — всегда полный бандл.
- Без прогресс-бара загрузки — спиннера достаточно.
- Без авто-снапшота перед restore — предупреждение + ручное скачивание.
